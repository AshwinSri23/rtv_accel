# RTV-Accel Project TODO & Implementation Roadmap

This document outlines the pending implementation tasks and milestones required to achieve full compliance with `RTV-Accel_ NPU ISA & Simulator Specification.md`.

**2026-09-08 precision pivot:** the NPU now targets native FP32 precision — INT8 quantization is out of scope. Most INT8-centric language below (in this doc, in the now-deleted `npu_compiler.py`'s comments, and in the spec doc itself) predates this decision. Concretely: Phase 2 is moot (it's entirely INT8 calibration work), and the original reason `tvm_backend.py` kept `npu_compiler.py` as the instruction-emitting backend — preserving hard-won INT8 scale semantics — no longer applied, since FP32 has none of that (confirmed directly against `pe_array.cpp`: FP32 GEMM/ELEMWISE_MUL/RMS_SCALE are the literal float operation, no fixed-point convention anywhere). This is what made 1.5 (retiring `npu_compiler.py` outright) tractable.

**2026-09-10 — Phase 1 complete.** Every item below is checked off: the TVM path (`tvm_backend.py` + `rtv_tvm/`) is now the sole compiler, `npu_compiler.py` is deleted, and the surviving shared device/runtime state lives in `toolchain/compiler_state.py`. `head_dim > compiler.tile_dim` (up to and including Qwen3-0.6B's real head_dim=128) is now supported throughout the attention path — added after Phase 1's initial completion, see 1.1's `head_dim > compiler.tile_dim` entry below; every attention-related item elsewhere in this doc that used to say "verified at head_dim=16 only" is stale as of that update. 92 TVM-path tests across 15 files (plus the pre-existing 28-case `test_tvm_path.py`, folded into that count) all pass, verified through a real `cmake` + `ctest` run, not just manual invocation. The KV-cache is now wired into a full multi-layer, multi-step decode loop (`_emit_model_kvcache_fp32`, verified in `rtv_tvm/test_decode_loop.py` across genuine separate `rtv_sim` invocations, not a single-shot batch) — see 1.1's "Wire the KV-cache into a full per-layer/per-model decode loop" entry. What Phase 1 does NOT cover, by design: genuinely batched (prefill-style) multi-row processing stays at the attention-core level, not wired into a decode loop of its own (decode is inherently single-token, so this was never on that loop's critical path); and Phases 2-3 below are separate, untouched efforts (Phase 2 is dropped/moot, Phase 3 is kernel-driver work this effort never touched — deliberately saved for last). Phase 4 (hardware/platform verification) was removed entirely: 4.1 needed physical ARM hardware this project doesn't target (development is x86-64 only), and 4.2 depended on coordinating with `rtv_core`, a separate project out of scope for this repo's own roadmap.

**2026-09-10 — real Qwen3-0.6B checkpoint loading, and a real architecture gap it exposed.** `toolchain/checkpoint_loader.py` (new) loads a REAL, downloaded Qwen3-0.6B checkpoint (`hf download Qwen/Qwen3-0.6B --include "*.json" --include "*.safetensors"`, ~1.5 GB) into exactly the shapes the FP32 TVM path expects — built on `toolchain/hf_loader.py`'s `SafeTensorsModel`, which turned out to need NO changes at all: it was already dtype-agnostic (BF16→FP32 widening, no quantization anywhere in it), only its original INT8-era caller (`generate.py`, retired) was precision-specific. The one real transformation needed is the same one the spec doc already documents hitting once before: HF's `nn.Linear` stores `(out_features, in_features)` and computes `x @ W.T`, while this project's GEMM wants B as `(in, out)` directly — every 2-D projection weight is transposed on load specifically to not repeat that bug. Verified in `rtv_tvm/test_checkpoint_loader.py`: real layer 0 (and a real 2-layer chain) run through `_emit_model_kvcache_fp32` and `rtv_sim` **at Qwen3's actual full dimensions** (hidden=1024, 16 heads over 8 KV heads, head_dim=128, intermediate=3072 — not a synthetic analogue), checked against a numpy reference built from the IDENTICAL loaded tensors. Skips cleanly (not a failure) when the checkpoint isn't downloaded locally, since it's a real ~1.5 GB fetch no fresh checkout or CI machine should be required to have.

**2026-09-10 — that gap closed: Qwen3's q_norm/k_norm now implemented.** Real Qwen3 applies a per-head RMSNorm to Q and K (`self_attn.q_norm.weight`/`k_norm.weight`, each a `(head_dim,)` gain shared across every head) *before* RoPE, right after projection/reshape. `_emit_rmsnorm_row_fp32` (and its underlying `_rmsnorm_prim_fp32`) gained `x_stride`/`out_stride` parameters — the same convention `_matmul_prim_fp32` already established for column-slice operands — so it can normalize one head's head_dim-wide slice of the wide Q/K projection buffer IN PLACE, without first de-interleaving that head into its own tight buffer. `_emit_attention_block_kvcache_fp32` gained `q_norm_addr`/`k_norm_addr` params (default `None`, so every pre-existing random-weight caller is unaffected); when given, it applies the shared gain to every query/KV head's slice, positioned between projection and the existing RoPE loop — matching real Qwen3's exact op ordering. Threaded through `_emit_transformer_layer_kvcache_fp32`/`_emit_model_kvcache_fp32` (`layer_weights[i]["q_norm"]`/`["k_norm"]`, via `.get()` so absence is a no-op) and `build_kvcache_model_dram_image` (broadcasts each to a genuine `(16, head_dim)` buffer, same convention as `gamma1`/`gamma2`, straight off `checkpoint_loader.py`'s already-extracted `q_norm`/`k_norm` — no loader changes needed). Verified two ways: `test_decode_loop.py`'s new `decode_2layer_gqa_qk_norm` case (random weights, independent of any checkpoint download) and `test_checkpoint_loader.py`'s existing two cases, whose numpy reference now applies q_norm/k_norm too (previously it deliberately skipped the step on both sides) — both pass. Real Qwen3-0.6B checkpoint values, run through the real compiler pipeline at real dimensions, now match an independent computation that is architecturally faithful up through q_norm/k_norm and RoPE (the one remaining gap to a bit-for-bit match against Qwen3's own published outputs is attending over a genuine multi-token context — every test here, including this one, still attends over "one real cached key, this step's own", the same documented simplification every earlier attention test used).

**2026-09-10 — that remaining gap closed too: real checkpoint through a genuine multi-step decode loop.** `rtv_tvm/test_checkpoint_decode_loop.py` (new) combines `test_checkpoint_loader.py`'s real weights with `test_decode_loop.py`'s multi-step round-trip harness: three genuinely distinct real token ids, embedded via the real (tied) embedding table, fed one at a time through `_emit_model_kvcache_fp32` across three SEPARATE `rtv_sim` invocations, with the KV-cache genuinely growing (each query head attends over every real cached key so far, not "one key") and each step's DRAM image spliced from the previous step's dump — the same real generation loop mechanics `test_decode_loop.py` already established, now driven by real Qwen3-0.6B layer weights (including q_norm/k_norm) instead of random ones. All three steps pass against a genuine incremental numpy reference. No source changes were needed to reach this — every piece (`checkpoint_loader.py`, `build_kvcache_model_dram_image`, `_emit_model_kvcache_fp32`, the multi-step round-trip pattern) already existed and composed directly; this was purely closing a verification gap between two things that had each been proven separately. 92 TVM-path tests across 15 files, 19/19 via `ctest`. **2026-09-10 — the runnable demo itself: `toolchain/generate.py` (rewritten).** The INT8-era `generate.py` (retired 2026-09-09) drove `NPUCompiler.compile_model()`/`compile_lm_head()`, both gone with `npu_compiler.py`'s deletion — this is a full rewrite against the current API, not a port, reusing `checkpoint_loader.py` for weights and the `tokenizers` library (already present in `.venv-tvm`, no torch — reads the checkpoint's own `tokenizer.json` directly) for text. Same host/device split the retired file already documented correctly: embedding lookup (a GATHER — LOAD_TILE has no indirect addressing) and argmax sampling (REDUCE_MAX has no index, and top-k/temperature are control flow this ISA has none of) stay host-side by necessity; `lm_head`'s projection also stays host-side, but for a narrower reason — it's one trivial CPU matmul, not worth a whole extra on-device program. Everything else — every transformer layer, RMSNorm, SwiGLU, attention, RoPE, q_norm/k_norm, the KV-cache — is `_emit_model_kvcache_fp32`, unmodified from `test_checkpoint_decode_loop.py`. Smoke-tested with `--n-layers 1` (a fast, deliberately-incomplete run to prove the driver LOOP itself: tokenize → per-step decode → detokenize, all wired correctly) — output is gibberish as expected with 27 of 28 layers missing, which is the correct outcome for that flag; per-step numeric correctness is already proven separately by the test suite. Not wired into `ctest` (it's a demo script with no numpy oracle of its own to check against, same as the retired file it replaces). Real dimensions make a FULL 28-layer run slow: ~9s/step at 1 layer scales roughly linearly, so ~4+ minutes per generated token at the real layer count — expected and architectural (codegen.py's own "each decode step is a fresh ~12M-instruction program" note), not a bug.

**2026-09-10 — two real bugs found running `generate.py` at actual 28-layer scale, both fixed.** A first full-model run crashed on step 5 with `ValueError: cannot reshape array of size 0` — a real, reproducible bug, not flakiness:

1. `generate.py` wrote a brand-new `step_N.img` file (a full copy of the whole DRAM image — ~1.7+ GB at Qwen3-0.6B's real size) for every decode step and never deleted the previous ones. `/tmp` on this machine is a 16 GB RAM-backed `tmpfs`, and by step 5 roughly 6 such images had accumulated (~11 GB), closing in on that cap. Fixed by reusing ONE state file path across every step instead of a fresh one per step — safe because `rtv_sim` fully reads `--dram-image` into its own in-memory buffer (and closes the file) *before* it writes any `--dump` output, confirmed directly against `src/simulator.cpp`'s ordering, so the same path can be both input and output. This never showed up in `test_decode_loop.py`/`test_checkpoint_decode_loop.py` because their configs are tiny (KB-scale images); 28-layer real weights was the first workload big enough to expose it.
2. The reason it failed silently instead of erroring: `src/simulator.cpp`'s `--dump` file-writing code called `std::ofstream::write` without ever checking whether it succeeded. When the full `tmpfs` made that write fail, it silently produced a 0-byte file with exit code 0 instead of a clear error — so the failure only surfaced three steps later in Python, reshaping an empty array, with no indication of the real cause. Fixed with a check after the write (`if (!out) { ...error...; return 1; }`) so any future write failure (full disk/tmpfs or otherwise) fails loudly and immediately, at the exact point it happens, instead of miles away in an unrelated caller.

**2026-09-11 — memoize the compile-time constants several "constant matrix via GEMM" helpers were rebuilding redundantly.** RoPE's rotate_half permutation matrix, the row0↔broadcast masks (`_emit_broadcast_row0_fp32`/`_emit_mask_to_row0_fp32`/`_emit_copy_slice_fp32`), the attention core's row0 mask, and the KV-cache's tail/append masks all build content that depends only on decode-step-global values (`head_dim`, `seq_k`, `pos`, `theta`, `row`, `valid_len`, `width`) — never on which head or layer is calling. Every one of them was rebuilding and re-staging a fresh, byte-identical copy on EVERY call anyway: at Qwen3-0.6B's real dimensions, RoPE alone calls `_emit_rope_fp32` 24 times per layer (16 Q heads + 8 K heads) × 28 layers = 672 times per decode step, all with the identical `(head_dim, pos, theta)` — meaning one 64 KB permutation matrix was being rebuilt 672 times for content that never changes within that step.

New `_get_or_build_const(compiler, key, nbytes, build_fn)` in `tvm_backend.py`: returns the DRAM address of a constant identified by `key`, building it only the first time that key is seen this decode step, via a new `compiler._const_cache` dict (`compiler_state.py`) that lives on the `NPUCompiler` instance — since a fresh compiler is created per decode step (the existing convention), the cache resets exactly when it should (new position → new step → new cache) with no explicit reset call needed. Wired into all seven call sites above.

**Important correction to how this was originally pitched** (as a "DRAM footprint AND instruction-count" win): measured directly, it is DRAM-footprint-only. Qwen3-0.6B's per-layer instruction count is bit-for-bit identical before and after (332,464 instructions/layer either way) — each head still needs its own real `LOAD_TILE`/`COMPUTE_GEMM` instructions to apply RoPE to *that head's own data*, regardless of whether the constant those instructions reference is shared or freshly duplicated. What actually shrinks is the redundant DRAM data itself: for a 2-layer real-checkpoint run, `_const_regions` dropped to 9 entries / 213 KB total (was on the order of ~150 redundant builds for those same 2 layers); at full 28-layer scale the redundant-constant category alone would otherwise total on the order of ~57 MB (analytically: ~2 MB/layer × 28), now a flat ~0.2 MB regardless of layer count. That 57 MB isn't a large fraction of the full DRAM image (dominated by ~1.7 GB of real weights), but it's exactly the kind of per-decode-step growth that contributed to the `/tmp`-exhaustion bug above, and a real, correct, low-risk win regardless of magnitude — separate from, and much smaller than, the still-unbuilt schedule-relocation optimization (which targets TVM's actual ~7.6s/layer compile cost, the thing this fix does NOT touch).

Verified via a new `rtv_tvm/test_const_memoization.py` (asserts the cache stays flat across 1→4 layers, and that RoPE's 18 calls in a 3-layer case collapse to exactly one cached entry each for its permutation matrix and its cos/sin table) plus the full existing suite (unaffected, since sharing an address changes nothing observable about correctness). 94 TVM-path tests across 16 files, 20/20 via `ctest`.

Both fixed, `rtv_sim` rebuilt, full 19/19 `ctest` re-verified (no regressions), and a small `--n-layers 1` smoke test re-run to confirm identical output to before the fix. This is the same kind of bug this whole project has hit repeatedly at every scale-up (RoPE's permutation matrix, `_emit_transpose_wide_fp32`'s stride default, now this): something that's silently correct at every size tested so far and only breaks once a genuinely bigger/more-real workload exercises the assumption nothing before it stressed.

  - [x] KV-cache — `tvm_backend._emit_kv_cache_append_fp32`/`_emit_kv_cache_tail_mask_fp32`, a real, GROWING multi-tile cache (not the same thing as the batched-multi-row work above — that's one 16-row TILE of independent rows attending to each other/themselves; this PERSISTS and GROWS K/V state across MANY decode steps/tiles, with later ones causally attending to every earlier one). Two pieces, both the same "constant matrix through GEMM" trick this codebase already leans on wherever hardware has no matching primitive: (1) append — `LOAD_TILE`/`STORE_TILE` only move whole 16x16 tiles (confirmed against `pe_array.cpp`: no sub-tile partial-row write opcode), so inserting one new token's row into an existing tile is done via `blended = mask_keep @ old_tile + mask_insert @ new_row_bcast`, two compile-time constant matrices (row index is a Python int) selecting "every row except the target" and "only the target" respectively; (2) tail-masking — the newest tile is usually only partially filled, so its unfilled rows (and any wholly-future tiles) must not contaminate the softmax, reusing `_emit_attention_core_fp32`'s EXISTING `mask_addr` parameter (built for causal masking already) with a per-column 0/-1e30 mask instead of a new mechanism. Verified two ways in `rtv_tvm/test_gemm_double_buffer.py`: exact correctness against a numpy reference for real multi-K-tile cases, AND a genuine cycle-count win via `rtv_sim`'s own serial-vs-db model (2.04x for an 8-K-tile matmul, 1.77x for a real SwiGLU composite) rather than just "doesn't crash." Two real findings on the way:
    - Double-buffering only the weight operand (B), matching `compile_linear`'s own scheme, measured as a complete NO-OP on `rtv_sim`'s cycle model — identical serial/db numbers with or without it. Root cause: `WAIT_SYNC` stalls to the LATEST unmet dependency, and A's un-overlapped reload (kept single-slot, reloaded fresh every step) has its full latency on the critical path every step regardless of how well B's prefetch overlapped. Buffering A too is what actually moved the number — a real difference from `compile_linear`'s design, not an oversight in copying it.
    - A double-buffering scheme that pre-issues BOTH tile k and k+1's loads before waiting on either (closer to `compile_linear`'s literal two-ahead algorithm) has a real hazard here that `compile_linear` doesn't hit: `LOAD_TILE`'s `dep_id` is a small, reused tag, and the simulator's `dep_done[dep_id]` is simply overwritten by each new load using that tag — issuing tile k+2's load before tile k's own load is ever waited on would silently make that wait check the WRONG tile's completion time. Sidestepped by prefetching only one step ahead: wait for step k fully, THEN prefetch k+1, THEN compute — `dep_done` always reflects exactly the load just waited for.
