# RTV-Accel Project TODO & Implementation Roadmap

This document outlines the pending implementation tasks and milestones required to achieve full compliance with `RTV-Accel_ NPU ISA & Simulator Specification.md`.

**2026-09-08 precision pivot:** the NPU now targets native FP32 precision — INT8 quantization is out of scope. Most INT8-centric language below (in this doc, in the now-deleted `npu_compiler.py`'s comments, and in the spec doc itself) predates this decision. Concretely: Phase 2 is moot (it's entirely INT8 calibration work), and the original reason `tvm_backend.py` kept `npu_compiler.py` as the instruction-emitting backend — preserving hard-won INT8 scale semantics — no longer applied, since FP32 has none of that (confirmed directly against `pe_array.cpp`: FP32 GEMM/ELEMWISE_MUL/RMS_SCALE are the literal float operation, no fixed-point convention anywhere). This is what made 1.5 (retiring `npu_compiler.py` outright) tractable.

**2026-09-10 — Phase 1 complete.** Every item below is checked off: the TVM path (`tvm_backend.py` + `rtv_tvm/`) is now the sole compiler, `npu_compiler.py` is deleted, and the surviving shared device/runtime state lives in `toolchain/compiler_state.py`. 73 TVM-path tests across 12 files (plus the pre-existing 28-case `test_tvm_path.py`, folded into that count) all pass, verified through a real `cmake` + `ctest` run, not just manual invocation. What Phase 1 does NOT cover, by design: genuinely batched multi-row processing and the KV-cache are built and verified at the attention-core level but not wired into a full per-layer/per-model decode loop with real projections (mechanical assembly of existing pieces, not a remaining open question); `head_dim > compiler.tile_dim` (e.g. 32) is unsupported throughout the attention path (K's per-head transpose and RoPE's intra-tile permutation both need generalizing to multi-tile first); and Phases 2-4 below are separate, untouched efforts (Phase 2 is dropped/moot, Phases 3-4 are kernel-driver and hardware-validation work this effort never touched).

Found and fixed two real bugs on the way:
    - `codegen.py` had `T.match_buffer`'s `strides` parameter available but silently ignored it everywhere — both `_tile_copy`'s LOAD_TILE *and* STORE_TILE pitch calculations used the buffer's own shape unconditionally. The STORE_TILE one was the more dangerous of the two: writing head h's output column-slice used `head_dim` as the row pitch instead of `n_heads*head_dim`, so row 1 of any head's write landed inside row 0's own span instead of the next head over — every row past 0 silently corrupted by whichever head's store ran after it. Never caught before because every prior test only ever *read* a strided buffer, never wrote one.

Fixed by using `is not None` instead of bare truthiness.

The only thing scoping this to one tile was the function's OWN internal buffers being hardcoded to `(M, M)` instead of `(M, seq_k)` — fixed by generalizing those. Verified against `rtv_sim` for square (32×32) and non-square (`seq_k=48,head_dim=16` and `seq_k=16,head_dim=64`) multi-tile cases in `rtv_tvm/test_attention_multitile.py`. This was previously (incorrectly) bundled with the genuinely-batched-queries limitation below — they're independent; only the latter needs `codegen.py` generalized further.
  - [x] Real Q/K/V/O projections around the attention core — `tvm_backend._emit_attention_block_fp32`, built while working toward multi-layer orchestration. Two conventions collide at this block's boundary and getting them right was the actual work: layer-level activations need "row 0 real, rest zero" (`_emit_rmsnorm_row_fp32`'s REDUCE needs it — confirmed directly: feeding it a genuinely replicated input summed 16x too much), while the attention core needs "all 16 rows identical." Bridged with `_emit_broadcast_row0_fp32` (replicate via GEMM against a compile-time one-hot matrix — no hardware broadcast primitive exists; a LOAD_TILE stride of 0 is reinterpreted as "not set," not a literal broadcast) and `_emit_mask_to_row0_fp32` (the inverse, masking back down). Found and fixed a real bug on the way: V was handed to `_emit_gqa_attention_fp32` as a wide column-sliced buffer, but that function expects K/V as separate CONTIGUOUS per-head blocks (K gets that naturally as a side effect of its transpose; V never had an equivalent step) — every head silently computed the same wrong, blended context until a `_emit_copy_slice_fp32` de-interleaving step (same one-hot-GEMM trick, this time with an identity matrix) was added for V too. Verified against `rtv_sim` in `rtv_tvm/test_transformer_layer.py`, including a GQA case (4 heads / 2 KV heads) that specifically exercises this. Still constrained to `head_dim == compiler.tile_dim` (16) — the per-head transpose only handles one square tile.
  - [x] RoPE — `tvm_backend._emit_rope_fp32`, wired into `_emit_attention_block_fp32`/`_emit_transformer_layer_fp32`/`_emit_model_fp32` via a new `pos=` parameter (a Python int, the decode step's absolute token position — same value forwarded to every layer, consistent with this whole codebase recompiling per decode step rather than carrying position as runtime state). Applied per-head to Q and K right after their projections, before the row0→replicated broadcast (RoPE is pure elementwise+permute, so it doesn't care about that convention boundary either side of it). Constrained to `head_dim == compiler.tile_dim` (16), same as the rest of the attention block: unlike `npu_compiler.py`'s `compile_rope` (which requires `head_dim >= 2*tile_dim` so the `rotate_half` partner lives in a whole separate tile), at `head_dim==16` the partner column is INSIDE the same tile, so the swap needs an actual intra-tile column permutation — done via GEMM against a compile-time permutation matrix (same "constant matrix via GEMM" trick as the row0/broadcast helpers, since there's no hardware permute primitive either). Verified two ways: `_emit_rope_fp32` alone against an independent numpy RoPE reference (not `NPUCompiler.rope_tables()` itself, to catch a convention mismatch between them — matched to 2.4e-7), and the per-head wiring inside the attention block against a per-head reference in `rtv_tvm/test_rope_attention.py`. That file also documents and checks a real structural property, not a gap: because this whole path's self-attention has exactly one DISTINCT key (replicated across the tile), Q and K always share the same RoPE angle, which cancels exactly in their dot product — so RoPE provably can't change this architecture's attention OUTPUT until a genuine multi-token KV-cache gives distinct keys at distinct positions. That's precisely why the wiring needed its own direct (non-output) test rather than trusting a full-layer before/after diff.
  - [x] Genuinely batched (non-replicated) multi-row queries — `tvm_backend._emit_softmax_rows_fp32`/`_emit_attention_core_batched_fp32`/`_emit_gqa_attention_batched_fp32`/`_emit_attention_block_batched_fp32`/`_emit_rope_batched_fp32`/`_emit_transformer_layer_batched_fp32`/`_emit_model_batched_fp32` — a full, real per-row batch of 16 GENUINELY DIFFERENT rows, not one row replicated. Needed two real pieces: (1) `codegen.py`'s `Codegen` gained a real `dim_m` instance attribute (default `TILE`, so every prior caller is unaffected) threaded through LOAD_TILE/STORE_TILE/EXEC_ALU/REDUCE/SCALAR_ALU's `dim_m` field, which used to be the literal constant `TILE` everywhere; (2) `tvm_backend._emit_softmax_rows_fp32` drives that at `dim_m=1`, once per row, since `schedule.py`'s own primitives (`schedule_reduce`/`schedule_tile_scalar`/`schedule_binary`) unconditionally split every axis into `TILE`-sized chunks (`sch.split(i, factors=[None, TILE])`) and simply cannot express a 1-row axis — there's no schedule-primitive route to this at all, only a direct hand-drive of `Codegen`'s primitives (same category of move as `_gemm_k_loop`/`_emit_swiglu_ffn_resident_fp32`). GEMM needed NO changes anywhere in this: `COMPUTE_GEMM` is inherently row-parallel (each output row depends only on its own input row), so it was already exactly correct for 16 distinct rows. Neither did RMSNorm or SwiGLU — see 1.5's `Fp32FullLayerCase` migration note for why RMSNorm in particular turned out to need zero changes. RoPE needed one new thing, `_emit_rope_batched_fp32` (per-row position instead of one shared `pos`), which caught a REAL, previously-invisible bug: `_emit_residual_add_fp32` had no output-stride parameter, so RoPE's final in-place write into a column-slice of a wider Q/K buffer used the wrong row pitch and silently spilled into the next head's columns — invisible in every prior row0-real-rest-zero test (corrupting a zero row with zero is not observable), only surfaced once genuinely non-zero data occupied every row. Fixed by adding `out_stride` to `_emit_residual_add_fp32` and passing it through from both RoPE variants. Verified against `rtv_sim` in `rtv_tvm/test_attention_batched.py` (core/GQA against an independent per-row-softmax numpy reference) and via the `Fp32AttentionCase`/`Fp32FullLayerCase` migrations below (real end-to-end parity against e2e_test.py's own math).
  - [x] KV-cache — `tvm_backend._emit_kv_cache_append_fp32`/`_emit_kv_cache_tail_mask_fp32`, a real, GROWING multi-tile cache (not the same thing as the batched-multi-row work above — that's one 16-row TILE of independent rows attending to each other/themselves; this PERSISTS and GROWS K/V state across MANY decode steps/tiles, with later ones causally attending to every earlier one). Two pieces, both the same "constant matrix through GEMM" trick this codebase already leans on wherever hardware has no matching primitive: (1) append — `LOAD_TILE`/`STORE_TILE` only move whole 16x16 tiles (confirmed against `pe_array.cpp`: no sub-tile partial-row write opcode), so inserting one new token's row into an existing tile is done via `blended = mask_keep @ old_tile + mask_insert @ new_row_bcast`, two compile-time constant matrices (row index is a Python int) selecting "every row except the target" and "only the target" respectively; (2) tail-masking — the newest tile is usually only partially filled, so its unfilled rows (and any wholly-future tiles) must not contaminate the softmax, reusing `_emit_attention_core_fp32`'s EXISTING `mask_addr` parameter (built for causal masking already) with a per-column 0/-1e30 mask instead of a new mechanism. Verified in `rtv_tvm/test_kv_cache.py`: append in isolation (the other 15 rows of a tile must survive untouched) and a genuine 20-decode-step simulation spanning 2 K/V tiles, checked step-by-step against a numpy reference that does real incremental single-query attention over all tokens seen so far at each step. Found and fixed two real bugs on the way, both in code this work was the first to actually exercise: `_emit_residual_add_fp32` had no output-stride parameter (RoPE's in-place write into a column-slice of a wider Q/K buffer used the wrong pitch, invisible in every prior row0-real-rest-zero test since corrupting a zero row with zero isn't observable — fixed by adding `out_stride`), and `_emit_transpose_fp32` likewise had no output-stride (a K-cache spanning more than one tile needs each tile's transpose written into its own COLUMN range of one wider row-major buffer, not a separate contiguous block — every prior use was single-tile, where this went unnoticed — fixed the same way). No 1/sqrt(head_dim) scaling — consistent with `_emit_attention_core_fp32` having none; assumed to happen upstream if a real graph needs it. Not wired into a full per-layer/per-model decode loop with real Q/K/V projections and RoPE-at-the-current-position (that's a mechanical assembly of pieces already built — attention core, RoPE, this cache — not a remaining unsolved question, but wasn't glued end-to-end this pass).

Partitioning itself (`patterns.partition`) runs and is verified for real (previously never exercised at all, since nothing could import `tvm_backend.py`). - [x] **1.2. Whole-Model TensorIR Scheduling (`toolchain/rtv_tvm/schedule.py`)**
  - [x] Strided operand loading for multi-head attention slices — done, see 1.1's multi-head/GQA item (`codegen.py`'s `_tile_copy` now respects an explicit `match_buffer` stride on both LOAD_TILE and STORE_TILE, verified against `rtv_sim`).
  - [x] Non-square matrix dimensions (>1 tile per operand) — done, see 1.1's ">1 K/V tile" item above.
  - [x] SRAM double buffering for GEMM K-tiles (`cache_read`, `cache_write`) — done via `codegen.py`'s new `Codegen._gemm_k_loop`, which replaces the generic per-K-step recursion with one that double-buffers BOTH operands (A and B, alternating each between two SRAM slots) and prefetches step k+1's tiles before step k's compute. `double_buffer` itself isn't an available `Schedule` primitive in this TVM build (checked directly), and `codegen.py` fully unrolls TIR into instructions itself rather than going through TVM's standard lowering passes, so this was real surgery on `_gemm`/`_tile_copy`'s emission order, not a schedule annotation. Verified two ways in `rtv_tvm/test_gemm_double_buffer.py`: exact correctness against a numpy reference for real multi-K-tile cases, AND a genuine cycle-count win via `rtv_sim`'s own serial-vs-db model (2.04x for an 8-K-tile matmul, 1.77x for a real SwiGLU composite) rather than just "doesn't crash." Two real findings on the way:
    - Double-buffering only the weight operand (B), matching `compile_linear`'s own scheme, measured as a complete NO-OP on `rtv_sim`'s cycle model — identical serial/db numbers with or without it. Root cause: `WAIT_SYNC` stalls to the LATEST unmet dependency, and A's un-overlapped reload (kept single-slot, reloaded fresh every step) has its full latency on the critical path every step regardless of how well B's prefetch overlapped. Buffering A too is what actually moved the number — a real difference from `compile_linear`'s design, not an oversight in copying it.
    - A double-buffering scheme that pre-issues BOTH tile k and k+1's loads before waiting on either (closer to `compile_linear`'s literal two-ahead algorithm) has a real hazard here that `compile_linear` doesn't hit: `LOAD_TILE`'s `dep_id` is a small, reused tag, and the simulator's `dep_done[dep_id]` is simply overwritten by each new load using that tag — issuing tile k+2's load before tile k's own load is ever waited on would silently make that wait check the WRONG tile's completion time. Sidestepped by prefetching only one step ahead: wait for step k fully, THEN prefetch k+1, THEN compute — `dep_done` always reflects exactly the load just waited for.
  - [x] "SwiGLU intermediate activations" staying resident in SRAM across ops, rather than round-tripping through DRAM between the projection and the elementwise SiLU/mul step — `tvm_backend._emit_swiglu_ffn_resident_fp32`. Turned out NOT to need fusing multiple ops into one bigger TVM schedule (the architectural change this item's earlier note assumed was required): checked directly against `src/simulator.cpp`/`pe_array.cpp` first, and found `COMPUTE_GEMM`'s C write is genuinely c_slot-ADDRESSED in hardware (16 independent 1KiB output slots, ISA v1.5) while `EXEC_ALU`'s operand addresses are just arbitrary SRAM addresses with no zone restriction at all — so an elementwise op can read directly from wherever a GEMM's own c_slot output landed, with no `LOAD_TILE`/`STORE_TILE` in between, using the ISA's existing multi-slot addressing rather than adding any new hardware behavior. `codegen.py`'s `Codegen` gained two small, general hooks for this: `skip_tile_io` (buffer names for which `_tile_copy` emits nothing, because the data's already at the right address) and `c_slot` (`COMPUTE_GEMM`'s actual hardware output slot, previously hardcoded to `0` — a latent bug for any future caller that ever needed a nonzero slot, now parameterized). Scoped to exactly the projection→activation link named by this item (the down-projection GEMM afterward still reads from DRAM normally — going further would mean the down-projection's own K-loop pulling tiles directly out of these c_slots, real additional surgery not needed to close this out) and to `2*(inter/16) <= 16` simultaneous output slots (gate's tiles + up's tiles), raising `NotImplementedError` past that rather than silently misbehaving. Verified in `rtv_tvm/test_swiglu_resident.py`: exact correctness against a numpy reference AND a genuine cycle-count win via `rtv_sim`'s own cycle model (1.34x for a 64×96 case), the same bar the GEMM double-buffering work used, plus a dedicated case confirming the capacity limit actually raises instead of overrunning silently.
  - [x] Model ping-pong activation DRAM buffers across transformer layers — done via `tvm_backend._emit_model_fp32`, which chains N layers alternating the activation buffer between two fixed DRAM addresses (layer 0: `x_addr`→`scratch_b`, layer 1: `scratch_b`→`scratch_a`, layer 2: `scratch_a`→`scratch_b`, ...) instead of allocating one buffer per layer. This is also what first required building ANY multi-layer orchestration on the TVM path at all — see the new `_emit_transformer_layer_fp32`/`_emit_attention_block_fp32` below. Verified against `rtv_sim` for 2 and 3 chained layers in `rtv_tvm/test_transformer_layer.py`, confirming the final result lands on the correct buffer for an odd layer count.
  - [x] Map all matched blocks to the 11 hardware TensorIR intrinsics (`rtv_tvm/intrin.py`) — for INT8 (pre-existing, 28/28 in `test_tvm_path.py`) and now also for FP32: added `gemm`/`mul`/`sumsq`/`rms_scale`/`silu`/`rowmax`/`rowsum`/`exp_sub`/`scalar_div`/`transpose`/`add` FP32 `TensorIntrin` variants (the originals were INT8-only; TVM's `tensorize` requires an exact dtype match, so they could never have matched an FP32 PrimFunc). All 11 now have FP32 coverage, exercised by the RMSNorm/SwiGLU/attention composites above (`transpose` is registered but not currently used by any dispatched composite — kept for when attention needs to transpose K itself rather than relying on an upstream permute).
